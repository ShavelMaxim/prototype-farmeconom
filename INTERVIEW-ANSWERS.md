# Объяснения проекта для собеседования

Это опора для разговора, а не текст для заучивания. Отвечайте коротко, затем открывайте соответствующий код и показывайте сценарий.

## Почему Next.js, если хостинг статический?

«Я выбрал Next.js для маршрутов App Router, общей компоновки, metadata и генерации отдельных страниц товаров. На GitHub Pages Server Components выполняются при сборке, а интерактивные части работают в браузере. Node.js-сервер на хостинге не нужен».

Где показать: next.config.ts, app/page.tsx, app/products/[slug]/page.tsx, .github/workflows/pages.yml.

Компромисс: для этой небольшой статической витрины React с Vite тоже подошёл бы и был бы проще. Next.js выбран осознанно как часть портфолио и основа для дальнейшего развития; он не обязателен для любого магазина. Новые товарные страницы требуют пересборки. SSR на каждый пользовательский запрос в этой публикации отсутствует. Главная содержит готовый каталог в HTML; параметры браузерного URL читаются через useSyncExternalStore после hydration. Отфильтрованная выдача рассчитывается на клиенте. Лишние loading/Suspense главной удалены после профилирования.

## Зачем Redux Toolkit?

«Корзина и выбранная аптека нужны шапке, каталогу, карточке и оформлению. Redux даёт единое состояние и явные операции изменения. Сумма и допустимость оформления вычисляются из товаров, количества и аптеки, а не сохраняются второй копией в store».

Где показать: src/entities/cart/model.ts, src/features/cart/summary.ts, src/app/store.ts.

Контекст React тоже подошёл бы для такого объёма. Здесь Redux помогает демонстрировать предсказуемые обновления и тестирование правил корзины. Не нужно складывать в него всё: фильтры живут в URL, форма — в RHF, черновик аптеки и открытые окна — в локальном React-состоянии.

## Зачем RTK Query без настоящего backend?

«RTK Query управляет результатами запросов, кешем и состояниями загрузки/ошибки. Компоненты используют одни и те же hooks, а источник данных можно менять. На Pages queryFn вызывает локальный адаптер. NEXT_PUBLIC_API_URL включает HTTP-режим общего каталога и оформления для будущего PHP API».

Где показать: src/entities/product/api.ts, src/features/checkout/api.ts, src/shared/api/base-api.ts.

Кеш зависит от аргументов запроса, включая поиск, сортировку и аптеку. Демонстрационная задержка помогает воспроизводить состояния. Это не реальный сетевой запрос в режиме Pages и не доказательство устойчивости PHP-сервера. Ответы каталога и оформления проходят runtime-проверку Zod. Все клиентские экраны используют общий кеш getInventory; при ошибке HTTP-режим не подставляет цены сборки. Контракт текущего API требует полного каталога с предложениями всех аптек; пагинация и настоящий PHP-сервис ещё не реализованы.

## Как восстанавливается корзина?

«При первом рендере используется известное начальное состояние. После hydration эффект читает localStorage, разбирает JSON, проверяет сохранение через Zod и отправляет restore. Затем подписка сохраняет изменения. До восстановления корзины действия недоступны, чтобы не затереть сохранённые данные».

Где показать: src/app/providers.tsx, src/entities/cart/model.ts.

Отдельный стабильный serverState передаётся React Redux Provider. Он сохраняет соответствие серверному HTML, если восстановление store произошло раньше hydration отдельной статической карточки. Store создаётся на экземпляр Provider. Повреждённый JSON/схема дают безопасную пустую корзину, отказ localStorage не мешает работе в текущем сеансе. localStorage не является авторизацией, серверным хранилищем или надёжной защитой цены.

## Первая загрузка и повторное обновление — в чём разница?

«Пока пригодного интерфейса или сохранённой корзины нет, показываю скелетон либо состояние восстановления. Когда выдача уже есть, сохраняю её при запросе, показываю обновление и временно блокирую добавление по устаревшим данным. При ошибке оставляю предыдущую выдачу и даю повторить запрос».

Где показать: Suspense и CatalogSkeleton, route loading.tsx, isFetching/isError в src/widgets/catalog/catalog.tsx.

В текущем каталоге есть начальные данные из сборки: отсутствие data в RTK Query не означает, что карточек вообще нет. Не нужно искусственно заменять пригодный контент скелетоном при каждом поиске. isFetching включает и первый запрос, и повторные; для состояния без данных следует отдельно учитывать их наличие. Конкретный вид route-level fallback зависит от статической навигации и кеша — не обещайте, что пользователь увидит его на каждом переходе.

## Почему выбор аптеки подтверждается отдельно?

«Аптека влияет на цену и возможность оформить корзину. Поэтому Radio меняет только черновик. Кнопка “Применить выбор” обновляет Redux, а отмена, крестик и Escape закрывают окно без изменения корзины. Товары не удаляются молча, недоступные позиции отмечаются».

Где показать: src/features/pharmacy/picker.tsx и E2E отмены/смены аптеки.

Показать: добавить гель → корзина → выбрать “У парка” → отменить → оформление доступно. Затем применить выбор → увидеть предупреждение и блокировку оформления. Итого включает выбранные позиции, в том числе недоступные; это теперь явно подписано.

## Что делают RHF и Zod?

«RHF управляет полями, ошибками и отправкой. Zod описывает допустимые значения и подтверждение демо-режима. Не использую Ant Form параллельно, чтобы не было двух владельцев состояния одной формы».

Где показать: src/widgets/checkout/checkout.tsx, src/features/checkout/model.ts, src/features/checkout/demo-checkout.ts.

На Pages повторная проверка оформления тоже выполняется в браузере. В настоящем магазине сервер обязан заново проверить цену, остатки, права и идемпотентность. Номер DEMO — временный результат сценария, он не подтверждает заказ.

## Что проверяют тесты?

| Уровень                     | Что проверяется                                                                                           | Чего это не доказывает                                    |
| --------------------------- | --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| Vitest: модели              | Количество, восстановление, смена аптеки, фильтрация, сумма, схемы                                        | Реальное поведение браузера и внешней БД                  |
| Vitest: оформление/Provider | Валидация демо-запроса и восстановление store                                                             | Работа будущего PHP API                                   |
| Playwright                  | Покупательский путь, reload корзины, изменение/отмена аптеки, URL Back, ошибки, прямые карточки, overflow | Полное соответствие WCAG, Safari и все устройства         |
| HTTP smoke                  | Страницы, JS/CSS по базовому пути и 404                                                                   | Интерактивность приложения                                |
| Actions                     | Воспроизводимая установка, проверки, сборка out, E2E и deploy                                             | Отсутствие всех дефектов и production-готовность магазина |

Не говорить «тестируется всё». Привести один пример пойманного дефекта: преждевременное применение аптеки при закрытии окна либо несогласованная hydration корзины. Рассказать, какой регрессионный сценарий защищает исправление.

## Что делать дальше в production?

Согласовать контракт с PHP API и проверять его ответы. Подключить MySQL через сервер, предусмотреть транзакции для резервирования, идемпотентность оформления, авторизацию и наблюдаемость. Протестировать доступность, реальные устройства и производительность. При необходимости обновляемых товарных страниц пересмотреть стратегию сборки/хостинга.

Не заявлять измеренный рост конверсии, улучшение скорости без замеров или знание внутренней архитектуры Фармэконом.

После frontend-итерации: getInventory объединяет источник данных каталога, карточки, корзины и оформления; use-catalog-params.ts содержит обработку URL/debounce и защиту от запоздавших обновлений. ProductCard вынесен из каталога. Диалог аптеки загружается по требованию, с явным возвратом фокуса. Axe и проверка reflow дополняют сценарные E2E; это не сертификация WCAG.

Профилирование cold start: docs/performance/PROFILING.md. Демо-кеш инициализируется до рендера в makeStore; HTTP-режим никогда не получает статические цены вместо проверки API. Prefetch ссылок выключен осознанно: меньше конкуренции при старте, первый переход запрашивает страницу по действию пользователя.
