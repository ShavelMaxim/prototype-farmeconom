# Следующая итерация: загрузка кода и декоративный рендеринг

6 ноября 2026. Исходное приложение — 5414929, документация — 2108df2. Цель — сократить работу браузера при сохранении стека и покупательского сценария. Оценка выше 90 — ориентир, а не гарантированный результат.

## Изменения

- Store принимает готовый каталог из Server Component. Демо-repository больше не входит в начальный клиентский граф. Тот же объект передаётся каталогу, без отдельной сборки второго набора данных.
- Фильтрация отделена от repository. Схемы ответа API загружаются динамически перед проверкой ответа; проверка не удалена и не перенесена после использования данных.
- Схемы URL, ID и сохранённой корзины используют официальный `zod/mini` из той же установленной зависимости Zod. Формы RHF и сложные контракты сохраняют полный Zod. Добавлены проверки границ длины/количества и trim, чтобы контролировать совместимость валидации.
- Диалог аптеки и Drawer фильтров предзагружаются по наведению или фокусу кнопки. При холодном старте без такого события они остаются отложенными. Клавиатура и возврат фокуса сохранены.
- `content-visibility: auto` применяется только к `aria-hidden` CSS-упаковкам с фиксированной высотой 198px (390px на странице товара). Названия, цены, ссылки и кнопки не помещены в пропускаемое поддерево. E2E проверяет геометрию после прокрутки и добавление последнего товара клавиатурой.
- Ранее добавленные `memo(ProductCard)`, узкие Redux-подписки, общий Intl.NumberFormat и RTK Query cache сохранены. Мемоизация простых вычислений повсеместно не добавлялась.

Анализ source maps фактически запрошенных при холодном старте скриптов: нет product/contracts, product/repository и Zod classic; Mini присутствует. Это проверка графа загрузки, не доказательство одинаковой скорости на всех устройствах.

## Контролируемое локальное сравнение

Три последовательных Lighthouse 13.6 прогона до и после: один URL `http://127.0.0.1:3100/prototype-farmeconom/`, Chrome headless, стандартный mobile preset и simulated throttling, холодный кеш. Обе сборки с `PROFILE_BUILD=true`. До — сохранённый out, после — текущая оптимизированная сборка. Во время замеров не выполнялись build и тесты. Сырые JSON: `round2/before-*.json`, `round2/after-*.json`.

| Показатель                                                 | До, медиана | После, медиана |
| ---------------------------------------------------------- | ----------: | -------------: |
| Performance                                                |  69 (67–74) |     73 (70–77) |
| LCP                                                        |       2,44s |          2,32s |
| TBT                                                        |      1466ms |         1081ms |
| CLS                                                        |           0 |              0 |
| Начальные JS transfer bytes, без gzip на локальном сервере |   1 084 364 |      1 061 592 |

TBT в этих прогонах снизился примерно на 26%, JavaScript — на 2,1%. Разброс оценки остаётся; три лабораторных прогона не являются полевым INP или гарантией ускорения каждого визита. Локальные абсолютные значения нельзя сравнивать напрямую с gzip-сборкой GitHub Pages.

## Отклонённый эксперимент

Проверен поддерживаемый Ant Design 6 `zeroRuntime` с build-time extraction стилей только используемых компонентов. Внешний CSS получился 268 717 байт до минификации; начальный JS почти не уменьшился. Три локальных прогона: Performance 60/65/60, LCP около 3,02s — хуже контроля. Медиана TBT 2312ms. Сырые результаты `round2/static-css-*.json` сохранены, изменение и дополнительная dev-зависимость удалены.

Глобальное встраивание большого CSS не добавлялось: оно увеличило бы HTML и дублирование в RSC, ухудшило отдельное кеширование стилей. Сохраняются ConfigProvider, AntdRegistry и обычные стили библиотеки. Скриншоты в `round2/visual` относятся к контрольной версии и этому эксперименту; финальные иллюстрации сохраняются отдельно.

## Изображения

Сейчас упаковки нарисованы CSS: растровых фотографий, которым требовались бы AVIF/WebP и `srcset`, нет. Уменьшать качество существующих изображений нечего. Когда появятся фотографии, для Pages нужны заранее подготовленные варианты размеров и `srcset`/`sizes` с учётом ширины отображения и DPR. Только ширина экрана не определяет нужное разрешение. LCP-изображение следует загружать сразу; изображения ниже первого экрана — лениво, с известными размерами. Встроенный серверный оптимизатор Next Image на GitHub Pages отсутствует.
